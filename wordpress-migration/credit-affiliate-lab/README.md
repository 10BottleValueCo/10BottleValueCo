# Synthetic credit and affiliate migration rehearsal

**This is an in-memory rehearsal, not a WooCommerce plugin, production importer, live connector, or financial ledger.** It cannot accept real-looking source IDs or emails. It has no database, filesystem, network, email, payout, refund, fulfillment or payment integration. Run `node test.mjs` from this directory. No customer credit or affiliate status is activated.

`plan()` preflights a fictional, explicitly synthetic normalized fixture, explicit synthetic customer/order mappings, a currency and optional previous in-memory state. Each row is retained separately with its source identity, relationships, original fixture values, and a digest to detect accidental state changes. Repeated identical input is idempotent; changes to prior rows or mappings fail. Duplicate keys, affiliate codes, credit emails and ledger order IDs, ambiguous mappings, malformed money, unknown or missing links and unrecognized fields fail the full plan. Missing previously planned rows are retained rather than deleted. A test checks that a later batch cannot reintroduce a retained account with a different ID. These safeguards and the digest are not authentication, transaction isolation or proof that a migration is production safe.

The fixture separates observed account balances, held and consumed ledger rows, adjustment history, affiliates, commission attribution and payout history. The plan reports separately recorded synthetic totals in integer cents. **It does not calculate spendable credit, subtract holds from balance again, determine payout liability, initiate payouts, or assert that records are settled.** Totals describe the accumulated fictional fixture including retained missing rows; they are not a current-source reconciliation. Credit activation and any affiliate payouts require separate implementation, source evidence and reconciliation.

## Source-code observations, not a verified current schema

The source migration `supabase/migrations/20261007100000_store_credit_checkout.sql` explicitly says `user_credits.id` does not exist in the inspected historical schema, and checkout code uses email and amount. The later source file `20261008220000_merit_store_credit.sql` defines a separate `store_credit_ledger` keyed by order with held/consumed state and a separate adjustment table. Its debit/hold flow updates `user_credits.amount`, so a migration must not blindly subtract held rows again. Whether those migrations are applied and what real rows actually contain remains unverified.

The source `supabase/migrations/affiliate_payouts.sql` describes an identity ID and payout amount, while `api/affiliate-account.js` reads affiliates by email/code, payout history, and attribution from both `affiliate_orders` and order metadata. Source history/policies can differ from the active database. Credit-account source IDs, synthetic mapping IDs, stricter positive decimal and timestamp rules, resolved customer ownership, and the simplified attribution fields here are **fixture conventions**, not statements about the live data. No real records have been accessed.

Before any real import: obtain authorized read-only access and a verified backup; inspect actual schemas, duplicates, rows, historical corrections and payout/credit semantics; build a durable mapping with collision handling; reconcile source versus destination including pending orders, reservations, prior holds, account identity and all historical financial records; preserve actual source IDs and provenance; design transaction and concurrent update handling; and test backup, recovery, delta synchronization, and side-effect suppression against a disposable staging store. Account/order ownership cannot be proven by this rehearsal. No claim is made that WordPress or WooCommerce currently provides credit/affiliate functionality. Exact schemas, existing credits, real rates and payouts remain unknown.
