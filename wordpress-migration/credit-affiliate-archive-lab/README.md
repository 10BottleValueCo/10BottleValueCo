# Synthetic credit and affiliate archive with identity reservations

**Disposable synthetic fixtures only. Not a production importer, customer credit ledger, affiliate system, or payout integration.** This experiment extends the sibling synthetic WordPress archive rehearsal with conservative identity reservations. It has no UI, REST route, cron job, payment integration, credit activation or payout handler; its explicit local/localhost/synthetic/disabled-HTTP/disabled-cron guard is necessary but not a complete isolation boundary. Never install on a real store or use actual customer records or credentials.

The dry-run validates exact fictional snapshots and checks durable synthetic identity claims across batches: customer and order mappings in both directions, credit email and owner, affiliate email and code, one credit hold per order, and an affiliate/order attribution pair. A mismatch or missing index on any archived record stops planning. The bounded audit examines at most 2,000 archive-related options and fails closed beyond that; this is not a production-scale mechanism or a tamper-proof audit. A version marker is reserved before identity claims and snapshot writes. Existing unindexed history or an unsupported marker fails rather than silently upgrading; a safe upgrade/rebuild process is not implemented. Dry runs and writes refuse to run while another archive lock is present.

Each claim and historical snapshot is stored as an inactive option, with claims reserved and parents written before dependent history. Batches remain nontransactional and can leave a version marker, orphan identity reservations, parent snapshots and a nonexpiring lock after interruption. Only the matching synthetic retry can reuse a reservation. Lock recovery requires the exact token and an explicit operator assertion that the worker is stopped; that assertion is not proof. No automatic cleanup or release of reservations is implemented. Other plugins or direct database changes do not honor this test lock, so no general concurrency guarantee is made. Historical balances and held rows remain separate and are not activated or recalculated.

Checks in disposable PHP-WASM/SQLite: `node test.mjs` 38/38; `TBV_TEST_GUARD=1 node test.mjs` 1/1; `node bridge-test.mjs` 5/5 synthetic planner-to-WordPress; `node recovery-test.mjs` 12/12 interruption after snapshot followed by PHP/WordPress restart; `node index-recovery-test.mjs` 11/11 interruption after the first identity reservation, restart, refusal of a competing synthetic identity and resumption of the matching batch. Run with `TBV_WP_TEST_RUNTIME` pointing to this project's disposable runtime. `node install-test.mjs` passed 6/6 using `TBV_ARCHIVE_TEST_ZIP` pointing to the lab ZIP. No `wp_mail` attempt or the tested payment-complete/named payout action was observed in the fixture; this does not verify arbitrary external plugin hooks.

The ZIP was not deployed or published. PHP request exit and runtime restart against SQLite do not prove behavior under physical power loss, concurrent writers, distributed cache, or MySQL/MariaDB. Real source schema, identity semantics, exports, migration, reconciliation, customer data, payments and Woo credit/affiliate functionality remain unverified or unimplemented.
