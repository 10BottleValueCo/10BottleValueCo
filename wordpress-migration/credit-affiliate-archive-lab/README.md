# Synthetic credit and affiliate history archive lab

**Disposable, synthetic data only. This is not a production importer, credit ledger, affiliate system, payout integration, or finished migration.** The PHP plugin registers no UI, routes, schedules, payment hooks, or payout actions. It accepts only explicitly synthetic snapshots with `sample-` identifiers and fictional email addresses, and requires a local WordPress environment, localhost site URL, a synthetic test constant, disabled WordPress HTTP and cron. These checks are test guards, not a complete network-security boundary. Never connect real records, credentials or a live store to this lab.

The in-memory `../credit-affiliate-lab` planner validates fictional normalized fixtures, retains historical IDs and explicit sample customer/order mappings, and builds snapshots. This lab can dry-run or store those snapshots as inactive, per-identity WordPress options. Each snapshot contains its source identity, currency, historical fields and synthetic links; account balance and held history stay separate. It does not calculate spendable credit, adjust balances, activate affiliate accounts, create actual Woo users/orders, send email, pay affiliates, refund or fulfill orders. `active` within a synthetic snapshot is historical data only. Invalid fields, nonsynthetic-looking identities, conflicting stored snapshots, missing parent snapshots and duplicate IDs in a batch fail preflight. A repeat with identical data is idempotent and altered history fails. Missing rows do not delete previously saved snapshots.

The plugin uses a single non-expiring test lock, writes parent records before dependents, and performs one option write per snapshot. A batch is **not transactional**: an interruption can leave a partial batch and a retained lock. Lock recovery requires an exact token and the operator's explicit assertion that the previous worker is stopped; the assertion is not proof. Recovery only removes the matching lock and does not remove history. Tests exit a synthetic PHP request after one write, restart the PHP/WordPress runtime against the same disposable SQLite database, and verify blocking, token checks, recovery and idempotent continuation. This is not a power-loss, concurrency, MySQL/MariaDB or production recovery guarantee. Additional validation is needed, including duplicate semantic identities across batches, full real-schema relationships, source/destination reconciliation, snapshot consistency and external integration side effects.

Run with `TBV_WP_TEST_RUNTIME` pointing to the isolated WordPress Playground runtime used by this project. `node test.mjs` runs 25 checks; `TBV_TEST_GUARD=1 node test.mjs` checks the runtime guard; `node bridge-test.mjs` passes synthetic output from the sibling JS planner into the WordPress archive (5 checks); and `node recovery-test.mjs` runs 12 interruption/restart checks. `install-test.mjs` uses `TBV_ARCHIVE_TEST_ZIP` to test an already-created lab ZIP through WordPress's plugin upgrader (6 checks). These tests use disposable SQLite copies and synthetic fixtures; they do not verify a live Supabase schema or inspect real records. A test filter observes calls to `wp_mail` and the fixture checks no payment-complete or named payout hook fired; this does not prove arbitrary third-party hooks are safe. No deployment or live database change is included.
