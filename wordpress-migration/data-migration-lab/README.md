# Customer/order migration planner — synthetic rehearsal

This is an **in-memory simulator**, not an importer, WordPress plugin, source connector or production-ready mapping. It deliberately only accepts synthetic `sample-` identifiers and `@example.invalid` emails. It performs no network, database, filesystem or payment operations. Run `node test.mjs`.

The simulator demonstrates batch validation, immutable source identifiers, exact decimal arithmetic, customer ownership links, item/subtotal and order-total checks, stable snapshots, repeat-run deduplication and all-or-nothing conflict handling. It preserves original historical status and a payment-evidence object verbatim: a source status alone is never converted into a new payment verification. It creates no WordPress users, orders, notifications, charges, refunds, credits, affiliate payouts, or stock changes.

`woo-proof.mjs` is a separate disposable local WordPress/WooCommerce experiment. It copies the isolated development SQLite database to a temporary directory, boots it with outbound HTTP and cron disabled, creates one example.invalid customer and one pending Woo order, verifies saved fields and side effects, and deletes the copy. Set `TBV_WP_TEST_RUNTIME` to the existing local WordPress test runtime to run it. This is a smoke test of Woo objects, not a production importer or a historical status mapping; the pending status is deliberately conservative for this synthetic proof.

The sample schema is an explicit, synthetic normalized contract, not the unverified production schema. The storefront uses a top-level order row and `metadata`/`items` (see `api/supabase/orders.js`, checkout in `artifacts/10-bottle-value/src/App.jsx` and migrations), but older rows may vary, guest/legacy ownership may be missing, and provider records have different evidence rules. Never manufacture customer identity or infer verified payments from email or a displayed order status. The item/subtotal and total formula here applies only to the fixture; real orders require source-specific reconciliation and cannot be presumed to have these semantics.

Before a real migration: obtain an authorized read-only inventory and backup; establish the persistent WordPress host and secure staging; examine actual schema, historical samples and payment evidence without publishing or logging customer information; decide authentication continuity and account reset treatment; build tested WooCommerce adapters including durable unique mappings and transactional/resumable writes; independently reconcile all money and links; address credits, holds, affiliates, refunds, tracking, addresses and legacy data; suppress outbound email, webhooks, gateway and fulfillment side effects; test recovery and final synchronization. Credit/affiliate data and actual user/order transfer are not implemented here. Live cutover remains separate from preview and requires the team's green light.
