# Synthetic source-shaped Woo migration planner

This is an offline, side-effect-free rehearsal for an adapter, **not an importer**. It has no Supabase, WordPress, WooCommerce, database, HTTP, mail, payment, fulfillment or filesystem integration. Run `node --test adapter.test.mjs` with Node.js; fixtures are created in test code, never loaded from customer exports. It plans customers and orders only. It does not read or transform real records, perform account migration, reconcile orders, create users, charge or refund, or migrate credits/affiliate history. It is deliberately unsuitable for production data.

## Evidence and boundaries

The checked-in project source includes code referring to orders, store credit and affiliate data. The narrow fixture in this lab is a synthetic contract informed by those source files, not proof of the active database schema or any actual customer records. No production rows, data types, constraints, permissions, complete source schema, counts or column contents were verified by this code. No assumption that this fixture covers all relevant source tables is warranted.

The checked-in `api/supabase/orders.js` source accepts an order request and may store that request in `metadata`; the test fixture in `tests/catalystpay-verification.test.mjs` uses `items` with `name`, `dose`, `quantity`, `price` and order metadata including subtotal, shipping and store credit. Payment SQL in `supabase/migrations/20261009020000_paylio_payment_bindings.sql` also stores a checkout snapshot in both metadata and items. These are source code and test examples, not verification of live historical records; the real nested shape could vary by pathway and contain private data. This adapter's synthetic projection intentionally narrows those fields and requires decimal **strings**, while source tests show some numerical values. That strict fictional contract does not establish compatibility with an actual Supabase export.

## Contract and safety

`plan(batch, previous?)` takes exactly `{synthetic:true,currency,customers,orders}`. Customer fixtures use `id,email,created_at`; orders use exactly `id,user_id,email,total,status,created_at,affiliate_commission_adjustment,metadata,items,payment_provider,payment_id,paid_at`. Every ID and payment reference must start `sample-`, emails must be `sample-…@example.invalid`, item names must start `Synthetic `, metadata and nested items must match the narrow fixture contract in the tests. IDs, explicit payment evidence, historical status, total and approved fixture metadata/items remain separate in the plan. Currency is explicit batch configuration, not inferred from the source total. Valid decimal strings are preserved exactly; the planner never calculates or invents shipping, tax, discounts, credit, totals or refund status. It sets Woo status, payment verification and amount reconciliation to `unresolved` / `unverified` pending operator mapping and reconciliation.

In the fictional contract an explicit null user ID is recorded as unlinked; it is never attached to a customer by email. Missing or malformed links, mismatched linked-order/customer email, duplicates, unknown fields, malformed shapes and conflicting changed records fail the entire batch with no proposed operations. The meaning of null in the real source remains unverified; this fixture does not migrate real guest orders. Duplicate email matching is deliberately exact within this fixture contract, and real case/canonicalization rules require investigation. Prior simulated source snapshots are validated and retained; identical reruns are `unchanged`, conflicting changes stop for review, and omission never deletes anything. State and source input objects are not modified. The simulated state is illustrative, not persistent, transactional, tamper-proof or a Woo mapping ledger; process interruption, concurrent writes, data-source snapshots and destination uniqueness are untested. A previously valid state with a changed record is not automatically updated.

Exact key allowlists reject `checkout_access_hash`, passwords, authentication tokens, unknown nested metadata and other unmapped fields, even when empty. Never select, transmit, or put these security credentials in fixtures or migration plans. Conversely, unknown order/business fields may be essential to historical preservation: halt and reconcile all required fields rather than dropping them, and decide separately how authentication will transition. The fictional test adapter deliberately refuses to process unknown information; that refusal is not a claim that omitted real information has been migrated. Nullable and other possible real values, timestamps/precision, historical status transitions, guest orders, account changes, identity collisions, discounts, taxes, refunds, order edits, payment-provider evidence, ledger movements, credit balances, affiliate codes, commissions/payouts, and duplicate data need independent discovery and reconciliation. Actual payment evidence may exist across additional tables beyond `orders`.

Before any real migration: verify an authorized, safe, consistent source snapshot and destination; document the complete live schema and business semantics; build least-privilege projections excluding credentials and checkout access hashes; reconcile counts, identities and amounts, retain immutable evidence and explicit operator decisions; establish robust idempotent destination mappings and recovery; prove no email, charges, refunds, payouts, stock changes, fulfillment or unrelated hooks can run; and rehearse against a realistic isolated WordPress/Woo host. This code alone proves none of those requirements, and does not authorize cutover. The owner and Ilja's agreed green light governs replacing the working storefront.
