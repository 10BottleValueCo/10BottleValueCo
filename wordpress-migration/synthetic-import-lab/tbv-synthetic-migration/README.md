# Synthetic migration lab — development only

This installable plugin scaffold contains functions for a synthetic-only rehearsal. It has no dashboard, CLI, REST endpoint, automatic import, or production workflow. Never install it on a live store or use real records. Functions refuse to run unless a disposable test runtime defines `TBV_SYNTHETIC_WOO_TEST`, `WP_HTTP_BLOCK_EXTERNAL` and `DISABLE_WP_CRON` as true. Source IDs and payment references must begin with `sample-`, customer emails must be `@example.invalid`, item names must start `Synthetic `, and the source fixture format is intentionally narrow.

`tbvsm_plan()` checks the entire fixture, identities, duplicate/missing ownership, dates, exact decimal totals, existing mappings and edited targets without writes. `tbvsm_apply()` acquires a database option lock, repeats preflight, and creates WordPress customer and pending Woo order objects. Repeated identical imports do not create duplicates. Original synthetic identifiers, historical status and synthetic payment references are recorded; a source 'paid' value does not mark the Woo order paid. It does not invoke payment completion or create refunds. The local runtime blocks HTTP and cron; apply suppresses WordPress mail while it runs. No operator credentials or customer data are included.

Two WordPress/Woo storage modes (HPOS and classic) are covered by local disposable SQLite tests. Mapping lookups include trash/unusual statuses; duplicate or edited destinations fail before planned writes. The fixture permits a single synthetic line, shipping and USD; there is no tax, discount, credit, affiliate, refund, variation, password migration or historical payment reconciliation. The order is intentionally pending and is NOT a real historical status mapping. Real provider records and actual Supabase schema remain unverified.

The importer now creates a persistent, non-expiring per-entity pending reservation before each write. A repeated import containing that source identity refuses to run while the reservation is pending. A fully saved target can be reconciled only if exactly one source identity exists, its complete saved fields match the original fixture and, for an order, its mapped customer identity matches. A partial or untagged object remains ambiguous and is never automatically adopted or deleted. Existing unrelated batches are not globally blocked by a pending reservation, so an operator must inspect unresolved reservations before continuing any migration. Source identities must be stable: this design cannot recognize the same source object presented under a different ID.

The lock and journal do not make a batch transactional. A crash or an error can leave partial records, an untagged orphan or a stale lock. Lock removal requires an exact lock token and an explicit caller assertion that the old worker has stopped; the boolean assertion itself is not proof. Clearing a lock does not clear reservations. Never clear a lock while the worker might continue; manually inspect ambiguous records on the disposable lab before any next step. There is intentionally no automatic timeout or destructive reset. There is no UI, retry scheduler or production recovery procedure. External plugins can attach their own hooks; tests do not prove arbitrary extensions cannot trigger side effects, and WP's HTTP block and mail filter are not a comprehensive sandbox. Real migration needs verified schema and credentials, stronger isolation, transactional/reconciliation design and migration-specific handling for credits, affiliates and payments. Do not use this as a production importer.

`recovery-test.mjs` exits six PHP requests at selected points (before creation, just after insertion, and after full save for both customers and orders), disposes and restarts the WP/PHP runtime against the same disposable SQLite database, and tests stale lock controls, repeated import blocking and exact-target reconciliation in both HPOS and classic storage. This is not a hard OS kill, power-failure or MySQL/InnoDB transaction test.

The adjacent `test.mjs` copies a disposable WP/Woo database, mounts this plugin, and deletes the test copy. Set `TBV_WP_TEST_RUNTIME` to the local isolated WP runtime. Run `test.mjs` and `recovery-test.mjs` normally for HPOS and with `TBV_TEST_CLASSIC=1` for classic; run `test.mjs` with `TBV_EXPECT_GUARD=1` for the runtime guard. These are development tests and not an installed-ZIP UI test.
